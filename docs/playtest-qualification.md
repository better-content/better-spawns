# Better Spawns playtest qualification (source assessment; not execution evidence)

## Active promise and ownership

The active pack's `docs/implementation.md` (Custom compatibility ownership) identifies **first-join spectator scouting and permanent spawn locking** as Better Spawns' responsibility. Its `index.toml` includes `mods/better-spawns-1.0.0.jar`; the pack currently **excludes Better World Management (BWM)**. The bundled `data/better_spawns/embark/embark.json` has `mode: none`; `SelectionDataRepository.load` also falls back to spawn-only when progression is configured but BWM is absent. Do not present class, kit, Embark, generation unlocks, starter Schematicannon, or World Management's supervisor as active first-world selection. Existing progression tests exercise a source policy against synthetic inputs, not the shipped reduced pack. Never load an existing BWM world in this reduced pack without a separate save-compatibility review.

On first join `ServerEvents.onPlayerJoin` enters spectator, sends menu/selection sync, and requires a current-site selection. The client `Shift+K` submits spawn-only selection via `ClientOnboardingActions`; `FinalizeSelectionPacket.handle` validates mode, current location/dimension and stable supporting site before writing the permanent respawn point, completing onboarding and releasing spectator. `PersonalRespawnEvents` and `PersonalRespawnService` keep the permanent point authoritative across bed use, death/clone and marker repair. `OnboardingIntegration` emits per-player finalized/selection events; `OnboardingVisibilitySync` distributes pending-player IDs. This repository does **not** choose a temperate world spawn or search biomes. Temperate-biome discovery and initial world-spawn selection must be tested at real world creation/entry by the pack or the actual active worldgen owner, not attributed to Better Spawns or simulated by teleporting into a favorable biome. BWM's proposed nine-neighbor candidate and successor-world policy are excluded/unpackaged source work, not an active testable promise.

## Existing evidence lanes and precise gaps

- **Deterministic unit/contract**: `./gradlew --no-daemon verifyFast` depends on `check`, `verifyRuntimeRefmap`, and `verifyNativeGameTestFixtureGuard`; `test` uses JUnit Platform and JaCoCo. Existing tests cover fallback configuration, dormant class/Embark catalogs, invalid pools/slots/items, progression-policy validation, client selection state, purge geometry, daylight spectator policy, marker resources and runtime-refmap build wiring. These tests do **not** exercise an actual first join, packet handling, client rendering/input, the active full pack, or persisted disk reload.
- **Native Forge server**: `./gradlew --no-daemon headlessGameTest` runs `runGameTestServer`; `./gradlew --no-daemon verifyFull` includes `verifyFast` plus that run. `BetterSpawnsGameTests` covers kit registry (dormant source catalog), marker terrain descent/reuse/repair/tool/drop, finalization event ordering/idempotence and bed-spawn lock. Newly authored `OnboardingMultiplicityGameTests` prepares 32 distinct sites and checks individual completion, idempotence and clone persistence at prefixes 8/16/32. This is an **unrun fixture**, not 32 online players, network contention, disk persistence, biome discovery or throughput proof. Native fixture lives in a fresh UUID under `build/gametest/`, preserves existing settings and rejects actual ERROR/FATAL log lines; it is not a pack launch.
- **Client + persistence**: no automated real client UI/packet first-join/rejoin test, no world-save/shutdown/restart/playerdata equality check, and no concurrent authenticated-client test in this repository. A full suite needs clean-world entry from an actual chosen seed: record first generated spawn and biome (including temperate-biome criteria from the active pack), join in spectator, scout and submit on the actual client, verify site/marker/identity, disconnect/rejoin, die/respawn, bed attempt, restart the **same** world and recheck. Neither `runGameTestServer` nor moving a test player via `/tp` validates first-spawn selection. Compare save before/after and retain backup; do not reset a shared player world for a test.
- **Scale**: native fixture probes *state separation* for 8, 16 and 32 synthetic player records; actual 8/16/32-player joins and selections need distinct live clients with unique UUIDs, interleaved start/rejoin/death, pending visibility sync, TPS/heap/tick/network samples and no cross-player spawn leakage. One client loop or 32 synthetic `ServerPlayer`s is not multiplayer performance evidence. Ensure no tests mutate an operator's world.

## Fixture acquisition and assertions

`OnboardingMultiplicityGameTests` uses the authored `gameteststructures/onboardingmultiplicitygametests.empty.snbt` via native GameTest registration; each stone support block is placed in the isolated fixture by `helper.setBlock(Blocks.STONE)` (not acquired from player inventory); clear feet/head positions are placed as air in the same fixture. `PersonalRespawnService.setRespawnPoint` creates the registered Better Spawns **respawn marker** in the support position as a result of site commit, not through a recipe or a fabricated loot source. All 32 `ServerPlayer`s are synthetic GameTest instances, each with its own generated UUID and fixture site. Existing marker GameTests likewise place test blocks directly or invoke native service preparation; the Schematicannon test resolves the registered Create item and grants it through `KitApplicator.giveStarterSchematicannon` for a dormant capstone source test, **not** a claimed shipped acquisition route. No named gameplay item/block in these fixtures should be counted as naturally acquired. For full-pack player-facing tests, map each required named item/block to its actual installed recipe, loot, trade, granted-kit or command/test-fixture provenance before declaring progression pass; missing acquisition is an unresolved gate, not an assumed recipe.
